1. WHAT THIS PROJECT IS
---------------------------------------------------------------------
A static recompilation (NOT emulation) of the Xbox 360 version of
"The Legend of Spyro: Dawn of the Dragon" (2008).
Developer: ETRANGES LIBELLULES - CONFIRMED (2026-10-25): the credits text inside the
executable (~0x82841060) reads "Sierra Entertainment, Inc." / "Etranges Libellules".
Engine: their IN-HOUSE engine; classes are prefixed "CK" (game-specific: "CKS08", S08 =
Spyro 2008). It is NOT Virtools (verified: no Virtools core classes). The menus use a
custom 2D "Flash"-named UI runtime that is NOT a SWF player (no SWF data or parser).
Publisher: Activision (NA).

CONFIRMED FROM THE DUMP (2026-10-25, read from Default.xex):
  Title ID 565507F9 ("VU" prefix = Vivendi/Sierra, game number 2041), media ID 379EF306
  XEX version 0.0.0.1 = original retail build, base version 0.0.0.1 (no title update
  applied). Disc 1/1. Region build "USA, Europe" (En,Fr,De,Es,It,Nl).
  Default.xex: 8,593,408 bytes, SHA-256 7C9C893065E7490295230EA2DC06E67C0D90DF451F6295CA699843BCB0A51171
  Image base 0x82000000, entry point 0x82413780, image size 0x8E0000 (~9.3 MB),
  encryption AES, compression basic (zero-run) - both handled by rexglue.
  Imports only 2 kernel libs: xboxkrnl.exe (261 imports) and xam.xex (76). NO d3d/xaudio
  import libs => D3D, audio etc. are statically linked into the exe, so the game's
  graphics layer is code inside the XEX (as expected for the HLE-renderer plan).
  No SystemUpdate/TU: \$SystemUpdate\su20076000_00000000 is just the 360 dashboard update.
GAME DATA (Data\, 415 files, 6.67 GB; shader pack separate):
  LVL000,010,020,030,040,050,060,080,090,100,110,120 (12 level folders), each with
    LVLxxx.KXE (main level data, ~100MB), STRxxxxx.KXE, 00..05<LLC>xxx.KXE (6 languages:
    En,Fr,De,Es,It,Nl), STREAMS\XENn.KCS, SPEECH\0..5_XENn.RWS (per-language speech)
  Root: 00GLC..05GLC.KXE (per language), GAME.KXE;  MOVIE\ (49 .VID = Bink 1 "BIKi",
    2.8 GB);  MUSIC\ (143 files, 1.5 GB)
  .RWS = RenderWare Audio stream (audio middleware, so likely RenderWare libs present)
  Shader\xenon\shfct.bin (17.6 MB) = precompiled shader pack -> Xenos microcode source
    for our shader translator (unverified: need to inspect).
  .KXE/.KCS formats unknown yet (KXE looks packed/compressed: not plain headers).

The game's PowerPC (Xenon) code in default.xex is translated ahead of time into
C++ by the reXglue SDK, then compiled to a native Windows x64 program. The
user supplies their own legal dump of the game. We never ship game assets.

As far as research showed (2026-10-25): no existing recomp of this game, and
no known DLC or title update for the 360 version. CONFIRM the title-update
question from the dump itself (XEX header version / any TU files).

2. THE GOALS (stated by the user, 2026-10-25)
---------------------------------------------------------------------
G1. Add a custom "Recomp" menu inside the game's own in-game settings menu.

G2. That Recomp settings menu holds the usual PC-port options:
      - FPS / frame-rate limit (incl. uncapped; watch for game logic tied to 30 fps)
      - VSync on/off
      - Display mode: fullscreen / borderless / windowed
      - Motion blur on/off
      - Anti-aliasing options
      - resolution / render scale, widescreen/aspect handling, UI scaling
      - anisotropic filtering, shadow quality, etc. (as the renderer allows)
      - controls/input, audio volume, language where applicable
      ("etc etc etc" - add whatever a good PC port has.)

G3. STRETCH GOAL: online co-op, with an on/off toggle in the Recomp menu.
      Reality check: the original has only LOCAL drop-in/drop-out co-op
      (Spyro + Cynder), no online play. Online co-op means building a
      netplay layer ourselves (deterministic lockstep or state sync over
      the existing local-co-op code path). Hard, and depends on how
      deterministic the game's simulation is.
      Approaches, in order to try (discussed 2026-10-25):
        1. Input-only lockstep: P2's pad slot reads from the network. Cheapest;
           needs a deterministic sim (RNG, float math, physics, threads, frame timing).
           Reading the game's 2P/input code (Ghidra) helps here, but the real test
           is a determinism experiment in the running game.
        2. Host streams video to guest, guest sends only inputs ("remote play").
           No determinism needed; adds guest input lag; needs video encode/stream.
        3. Sync actual game state (positions/health/enemies). Hardest, most fragile;
           needs deep decompile of 2P code. Last resort. Do it only after the base
      port is solid, and say honestly how feasible it turned out to be.

G4. THREE selectable renderers, chosen in the same Recomp menu:
      a) reXglue  - the SDK's built-in Xenos GPU emulation (rexgpu-xenos
                    plugin; Xenia-derived; D3D12 + Vulkan). Compatibility baseline.
      b) Vulkan   - OUR OWN renderer, talks to Vulkan directly.
      c) plume    - OUR OWN renderer on top of renderbag/plume (RHI over
                    D3D12 + Vulkan, as used by Unleashed Recompiled).
    Chosen design for (b) and (c): HIGH-LEVEL replacement. The game links
    Microsoft's Direct3D 9-style Xbox library statically. After recompiling,
    find those D3D functions (CreateTexture, SetRenderState, DrawPrimitive,
    Resolve, Present, ...) and replace them with our own implementations that
    call the modern API. This is what keeps Xenia out. We still need:
      - Xenos shader microcode -> HLSL/SPIR-V (XenosRecomp-style translator)
      - 360 texture untiling / endian swap / format conversion
      - handling of EDRAM/resolve tricks only where the game really uses them
    (b) and (c) should share the shader + texture code; they differ only in
    the backend (raw Vulkan vs plume).
    SWITCH POINT: reXglue already loads GPU backends as plugins:
      include/rex/system/gpu_plugin.h  (rex_gpu_abi_version, rex_gpu_create),
      cvar `gpu_plugin` in src/ui/rex_app.cpp, DLL name rexgpu-<name>.dll.
    Our Vulkan/plume renderers are natural additional plugins.

G6. MODDING SUPPORT (added 2026-10-25). Three layers, build in this order:
      1. Asset replacement: loose files in a `mods` folder override game assets
         (textures/models/audio/text/video). Hook the filesystem virtualization
         layer in reXglue. NEEDS the game's archive format reverse-engineered
         (Etranges Libellules custom engine) + an extract/repack tool. Design the
         file-override path from the start.
      2. Code mods: a hook API (run code before/after/replace recompiled game
         functions), like Unleashed Recompiled. After the base port runs.
      3. Script/config mods (e.g. Lua or text tweaks). Optional, later.
      4. LEVEL MODS (user asked 2026-10-25): maybe, hardest asset type. A level =
         geometry+textures, collision, entity placement, scripts/logic, lighting,
         nav/camera data. Feasibility depends entirely on the game's level file
         format (check early when the dump arrives; note how decodable it is).
         Order: decode format -> extract/view a level -> edit/replace pieces ->
         build exporter/importer tools (e.g. Blender) so others can make levels.
    Mod list with enable/disable + load order lives in the Recomp menu.
    Mods stay separate from game files; never mix copyrighted assets into mods.
    Open question for user: which mod type matters most (assets vs gameplay)?

G5. Keep a log of every step (the WORK_LOG file) and this overview, both in the
    project folder, so context can always be recovered.
